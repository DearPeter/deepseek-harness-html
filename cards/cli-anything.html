CLI-Anything：把软件变成 Agent 能直接调用的命令

它不改界面、不做截图识别，也不要求软件先有 API。做法是把真实软件的后端包一层结构化命令行—— Agent 发命令、拿 JSON，人类看可读输出。不截图，不点击，不依赖 MCP。

01它到底在干什么

一句话：Making ALL Software Agent-Native。这句口号写在仓库首页，中文直译就是"让所有软件都能被 Agent 直接调用"。 它不自建软件，也不重写软件，而是在软件后端和 Agent 之间补一层东西——一层用命令行表达、用 JSON 回答的接口层。

这层的形态很朴素：一个可执行的 pip 包，名字是 cli-anything-<software>。Agent 执行它、读到结构化结果、 再决定下一步。软件原本的功能一个不少，因为命令调用的就是软件自己的后端引擎，而不是替它做的阉割版。

冷静一句

它更像是给软件补一层可被 Agent 调用的接口层，而不是让 Agent 学会用软件。

02Agent 为什么用不了真实软件

大模型会推理，但它在软件面前没有手。要让 Agent 真去改一张图、剪一段视频、调一个 CAD 装配体， 目前只有三条路，而三条都不好用。

  1. GUI 自动化：截图 + 点像素 界面一改坐标就废，按钮位置漂移、弹窗遮挡、分辨率缩放都能让整条流程崩掉。它看起来能用，但维护成本随软件版本线性上升，而且 Agent 永远不知道自己点开了什么。
  2. API 封装：只覆盖能力的一小部分 专业软件的 API 往往只暴露了核心功能的一小撮，画面渲染、时间线、图层、滤镜链这些真正值钱的部分根本不在接口里。而且每家接口风格都不一样，接十个软件就要维护十套适配。
  3. 重写一个阉割版：丢掉 90% 专业功能 为了让 Agent 能用，干脆自己写个简化版。结果做出来的东西专业用户一天就弃用——因为它不是那个软件，只是一个长得像它的玩具。

这三条路的共同问题是：它们都在"界面"和"能力"之间做取舍。CLI-Anything 的赌注是——不用取。

03为什么答案是命令行

把接口做成 CLI，不是怀旧，是因为命令行对 Agent 恰好有四个别处凑不齐的性质。

命令行作为 Agent 接口的四个性质
性质具体表现对 Agent 意味着什么
结构化 默认双输出：人类看表格与进度，Agent 加 --json 拿机器可读结果 不用猜、不用正则从自然语言里抠数据，读到的就是字段
可组合 命令可以串、可以循环、可以带状态连续执行 多步工作流能被写成脚本，而不是靠模型临场记住上下文
自描述 --help 说明语法，SKILL.md 说明用途 Agent 可以自己发现、自己确认参数，不必由人提前写死提示词
确定性 同一条命令永远得到同样结果，失败有非零退出码 可重放、可断言、可写进测试；不依赖像素是否对齐

04七阶段流水线

这是这个项目真正的核心，也是它区别于"让模型自由发挥写个脚本"的地方： 给一个软件造 CLI 是一条固定的七阶段流水线，中途还插了一道 6.5。每一阶段都有名字、有产出物、有验收方式。

  1. 1

    Codebase Analysis 代码库分析

    读后端引擎（如 MLT、GEGL、bpy）、数据模型（XML / JSON / 二进制）和已有 CLI，把 GUI 上看得见的操作映射回底层 API 调用。

    产出软件专属 SOP 文档，例如 GIMP.md
  2. 2

    CLI Architecture Design 命令行架构设计

    按软件本身的领域划分命令组，定状态模型（用 JSON 工程格式承载），定双输出格式（人类 + JSON），定渲染管线怎么落到文件上。

    产出命令组划分、状态模型、输出契约
  3. 3

    Implementation 实现

    用 Click 写命令行，默认进入 REPL（统一由 ReplSkin 提供），所有命令支持 --json，全局会话状态与 undo / redo 可用。

    产出agent-harness/cli_anything/<software>/
  4. 4

    Test Planning 测试计划

    先写计划再写代码：单元测试计划、E2E 测试计划，以及真实工作流场景（不是玩具用例，是"用户真会这么干"的串行操作）。

    产出TEST.md 上半部分
  5. 5

    Test Implementation 测试实现

    test_core.py 用合成数据跑单元，test_full_e2e.py 用真实文件跑端到端，多步工作流连续验证，输出要过像素级或格式级检查；另有 TestCLISubprocess 通过子进程验证已安装命令真的可用。

    产出可运行的测试套件
  6. 6

    Test Documentation 测试记录

    跑 pytest -v --tb=no，把结果与覆盖缺口一起写进文档——不是只写"全部通过"，缺口也要留痕。

    产出TEST.md 下半部分
  7. 6.5

    SKILL.md Generation 插入阶段

    skill_generator.py 从 Click 装饰器、setup.py、README 里抽取元数据，生成带 YAML frontmatter 的 SKILL.md。

    这一步是整个设计的枢纽：有了它，Agent 才能自己发现这个 CLI 存在、知道它干什么，而不需要人去改提示词。

    产出SKILL.md
  8. 7

    PyPI Publishing 发布

    setup.py + cli_anything.* 命名空间包 + console_scripts 入口，本地先 pip install -e .，再用 which 确认命令真的挂上了，最后才发。

    产出PyPI 上的 cli-anything-<software>

注：官方文档就写作「Phase 6.5」，它是插在测试记录与发布之间的补充阶段，不是第八阶段。这里照原样呈现。

05CLI-Hub 与三种入口

造出来的 CLI 需要一个分发的地方，这就是 CLI-Hub：一个 registry（registry.json），目前收录 79 个 CLI。 它支持四种安装源——pip、npm、brew、以及系统自带工具。

围绕它有三种完全不同的使用姿势，取决于你是谁、要做什么。

三种入口
如果你的目标是做法
直接用现成的 装 cli-anything-hub，用 cli-hub 的七个动作管理全部 CLI
让 Agent 自己会找 给 Agent 装一个 meta skill，之后它自己知道去哪儿找、怎么装
给没有 CLI 的软件造一个 装 CLI-Anything 插件或 skill，对目标软件跑一条生成命令，走完七阶段

入口一：直接用现成的

# 装 hub 本体 pip install cli-anything-hub # 然后就有了一套统一的管理动作 cli-hub list # 看有哪些 cli-hub search <词> # 按关键词找 cli-hub info <名> # 看某个 CLI 的详情 cli-hub install <名> # 装到本机 cli-hub update # 批量更新 cli-hub uninstall <名> cli-hub launch <名> # 直接进 REPL

入口二：让 Agent 自己会找

给支持 skills 的 Agent 装一个 meta skill。装完之后，你只要说"帮我把这个视频的音轨抽出来"，它会自己去 registry 里翻。

npx skills add HKUDS/CLI-Anything --skill cli-hub-meta-skill -g -y

入口三：给没有 CLI 的软件造一个

装好 CLI-Anything 插件或 skill 后，把目标软件或仓库丢给它，它会照着七阶段走一遍。

# 在 Agent 里执行，参数是软件路径或仓库地址 /cli-anything <软件路径或仓库>

官方主页与 CLI-Hub 在线目录在 clianything.cc，另有 GitHub Pages 镜像。

07四个官方 demo，看 Agent 到底做了什么

官方 demo 值得看，是因为它们展示了同一套动作：Agent 不是在"操作界面"，而是在连续下发命令、 每一步都生成预览、并把每一步的状态记进轨迹文件。

  • FreeCAD逐步建模

    Agent 一步一步搭出一台 Curiosity 风格的火星车：悬挂、轮组、车体逐件生成。 全程用 preview 与 preview live 看中间态，同时写入 trajectory.json， 把每一步命令对应到哪一帧视觉状态都记下来——这既是调试手段，也是回放依据。

  • Blender硬表面建模

    主题是一台硬表面的轨道中继无人机。同样是 preview + live + trajectory 的组合： 建模不是一次成型，而是"改一点、看一帧、再改"的循环，循环由命令驱动。

  • Draw.io限时任务

    约 4 分钟从零画出一张完整的 HTTPS 握手生命周期图，最后产出 .drawio 源文件与 .png 图。 这个 demo 的说服力在于"限时"——它证明的不是能画，而是速度。

  • Godot端到端管线

    完整游戏 E2E 管线。这是所有 demo 里跨度最大的一个：不是单点功能，而是从工程到产物的一整条链路。

另有 Slay the Spire II、Kdenlive、Shotcut、VideoCaptioner 等 demo。官方称覆盖 18 个 demo 应用。

08和相邻方案放在一起看

这张表不是为了证明 CLI 最好，而是标清楚四条路各自在哪一格会失手。 MCP 不是敌人，是另一条路：它解决的是"协议怎么统一"，CLI-Anything 解决的是"软件本来没有接口"。

四种让 Agent 使用软件的方式
维度 GUI Agent / RPA 普通 API 封装 MCP Server CLI-Anything
交互方式 截图 + 点击HTTP 调用协议调用命令行 + JSON

09局限与冷静判断

57,789 star 的增速会让人误判成熟度。把宣传语剥掉之后，有几件事必须先说清楚。

  • 依赖源码。只有编译好的二进制、需要反编译时，harness 的质量和覆盖率会显著下降。这一点官方 README 自己就写了。
  • 依赖软件本体。装了 CLI 不等于装了能力——GIMP、Blender、LibreOffice 这些上游软件还得自己装。CLI 是接口，不是替代品。
  • 79 个 CLI 不等于"任何软件"。口号是 ALL Software，实际覆盖面仍在早期。用"能跑 79 个"去推"能跑任何软件"，是明显的跳跃。
  • 生成质量参差。CLI 以社区贡献为主，仓库有 236 个 open issues，部分 CLI 版本还停在 v0.1.x。同名不同质的情况会存在。
  • "2,461 tests passing" 是仓库汇总口径。它统计的是整个仓库的测试总量，不等于每个 CLI 都有同等覆盖。看单个 CLI 时要看它自己的 TEST.md。
  • 热度与生态之间有明显时间差。5.7 万 star 建立在一个还很薄的生态上——文档、教程、踩坑记录都还没跟上。现在入场，你遇到的问题大概率没人踩过。

换个角度说：它解决的是"接口有无"，不是"接口好用"。能不能稳定跑起来，一半取决于你选的软件，一半取决于那个 CLI 的贡献者写得认不认真。

10三条上手路径

按投入从低到高排。第一条五分钟能跑通，第三条是按天算的活。

路径 A只想用，不想造

适合先验证"这东西到底行不行"。装 hub，挑一个你熟的软件，跑一条命令看输出。

pip install cli-anything-hub cli-hub list cli-hub info <你熟的软件> cli-hub install <同名> cli-hub launch <同名>

路径 B让 Agent 自己找工具

适合已经在用 Claude Code / Cursor / OpenClaw 这类支持 skills 的环境。装完 meta skill 就不用记住命令名了。

npx skills add HKUDS/CLI-Anything --skill cli-hub-meta-skill -g -y

装完之后直接说需求，例如"把这个工程里的贴图批量压到 2K"，Agent 会自己去 registry 里找现成的 CLI。

路径 C自己造一个

适合目标软件没人做过、而你有它的源码。这条路要按七阶段走完，别跳步——尤其是第 4、5 阶段，跳过就没有可信度。

# 1. 让 Agent 按七阶段生成 /cli-anything <软件路径或仓库> # 2. 本地装起来验证入口挂没挂上 cd agent-harness pip install -e . which cli-anything-<software> # 3. 跑测试,把结果写回 TEST.md pytest -v --tb=no
